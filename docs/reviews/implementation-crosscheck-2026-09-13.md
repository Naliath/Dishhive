**Confirmed technical oversights, in priority order**

1. **P1 — A human facts confirmation can still be overwritten (R2).** `ApplyFactsAsync` checks the confirmation version after loading, but only `Recipe.Revision` is an EF concurrency token. The facts endpoint increments `FactsConfirmationVersion` without changing that revision. A human confirmation between the worker's final read and its commit therefore does not invalidate the worker's update. A PostgreSQL save interceptor reproduced this exact interleaving: the final row was `AiDetected` with human confirmation version `1`. Make the confirmation state part of the atomic write condition and handle a lost race as superseded work. Evidence: [`ApplyFactsAsync`](../../src/Dishhive.Api/Services/Facts/RecipeFactsAssessmentService.cs#L289), [concurrency mapping](../../src/Dishhive.Api/Data/DishhiveDbContext.cs#L143), [`Replace`](../../src/Dishhive.Api/Services/Facts/RecipeFactsStateService.cs#L32); test `HumanConfirmationBetweenWorkerReadAndCommit_MustNotBeOverwritten`.

2. **P1 — An exception before intent normalization bypasses explicit restrictions (R3).** Invalid returned intent and a negative capability verdict correctly yield an incomplete response, but a provider exception or timeout reaches the general catch while `request.Intent` is still null. The fallback is then validated against an empty intent and may be declared complete. The probe requested saved recipes only and received `Complete; Freezer soup`. Two live multi-source runs likewise returned complete freezer plans after approximately 60-second failures. Preserve an explicit unresolved-intent requirement on every pre-normalization failure and return a visible gap. Evidence: [`Complete` and the catch path](../../src/Dishhive.Api/Services/Suggestions/LlmMealSuggestionService.cs#L360); test `IntentProviderFailure_MustNotReturnCompleteFreezerPlanForLocalOnlyRequest`.

3. **P1 — Rules fallback loses the generated attendee set and local candidate version (R4/R6).** Rules suggestions leave `AttendeeIds` empty and do not populate `CandidateVersion`. Acceptance interprets the empty attendance as the household default, dropping explicitly requested guests. For linked local recipes, `StoreBatchAsync` records a null reviewed revision, which fails comparison against the unchanged recipe's revision and returns `needsReview`. Both failures were reproduced across generation, durable batch storage, and PostgreSQL acceptance. Normalize every provider's final suggestions with resolved attendees and candidate versions before storage. Evidence: [rules suggestions](../../src/Dishhive.Api/Services/Suggestions/RulesMealSuggestionService.cs), [batch revision extraction](../../src/Dishhive.Api/Services/Suggestions/MealSuggestionAcceptanceService.cs#L34), [attendance and revision checks](../../src/Dishhive.Api/Services/Suggestions/MealSuggestionAcceptanceService.cs#L156); tests `SelectedGuest_MustSurviveRulesFallbackAndAcceptance` and `UnchangedLocalFallback_MustRemainAcceptable`.

4. **P1 — Reviewed versions do not protect changed facts or reservation identity (R6).** Changing a recipe's human-confirmed classes after review still returns `created`, because its `local:<revision>` version does not include the facts confirmation version. Acceptance checks attendee activity but never revalidates dietary constraints. It also stores the reviewed freezer reference/quantity but does not compare them with the submitted values: clearing both in the request creates the meal without reserving stock. Persist the relevant facts/attendee/constraint snapshot, revalidate current compatibility, and take reservation identity from the stored candidate or explicitly require another review. Evidence: [candidate comparison](../../src/Dishhive.Api/Services/Suggestions/MealSuggestionAcceptanceService.cs#L147), [version helper](../../src/Dishhive.Api/Services/Suggestions/SuggestionCandidateVersion.cs), [candidate model](../../src/Dishhive.Api/Models/MealSuggestionBatch.cs); tests `ChangedFactsConfirmation_MustRequireReviewOnAcceptance` and `ClientCannotDropReviewedFreezerReservation`. External content hashes also omit quantities, steps, time, and the assessed classes at their call sites; the hash alone is not full requirement revalidation.

5. **P2 — A restart can strand running enrichment jobs indefinitely (R2).** Expired leases are recovered only once at startup. If the application restarts before a crashed worker's ten-minute lease expires, that job remains `Running`; subsequent polling only claims `Pending` rows. The probe ran startup recovery with a still-valid lease, waited for expiry, then confirmed that no job could be processed. Sweep expired leases during normal queue polling, with an atomic claim/ownership mechanism. Evidence: [startup recovery](../../src/Dishhive.Api/Services/Facts/RecipeFactsAssessmentService.cs#L116), [`ClaimNextAsync`](../../src/Dishhive.Api/Services/Facts/RecipeFactsAssessmentService.cs#L221); test `LeaseExpiringAfterStartup_MustBeRecoveredByRunningWorker`. Job claiming/coalescing also lacks a database ownership/concurrency condition, and enqueue occurs after the recipe save rather than in the same transaction; these are additional source-confirmed durability gaps.

6. **P2 — Translation builds chunks that the AI gate rejects (R8).** The chunker budgets four characters per token while the gate admits two. A valid recipe with sixteen 1,900-character steps produces a chunk accepted by `BuildChunks` and rejected before any provider call with `AiInputBudgetExceededException`. Use one budgeting policy including system text, schema, retry additions, and output headroom, then chunk to that policy. Evidence: [chunk sizing](../../src/Dishhive.Api/Services/Facts/RecipeLocalizationService.cs#L148), [gate admission](../../src/Dishhive.Api/Services/Ai/AiExecutionGate.cs#L192); test `TranslationChunks_MustFitTheSharedExecutionGate`.

7. **P2 — Concurrent retries of the same freezer suggestion return a false failure (R6).** The idempotency lookup occurs before the stock lock. Both requests can see no existing meal; after one commits, the other sees depleted stock and returns `stockUnavailable` before checking the suggestion key again. PostgreSQL returned `created / stockUnavailable` instead of `created / alreadyApplied`. Stock was not over-reserved, but the retry result is incorrect. Recheck idempotency inside the serialized acceptance section before rejecting unavailable stock. Evidence: [initial key lookup](../../src/Dishhive.Api/Services/Suggestions/MealSuggestionAcceptanceService.cs#L112), [stock rejection](../../src/Dishhive.Api/Services/Suggestions/MealSuggestionAcceptanceService.cs#L231); test `ConcurrentRetriesOfSameFreezerSuggestion_AreIdempotent`.

8. **P2 — The final checker does not fully validate meal slots (R3).** A dessert alone satisfies its day-coverage check even when the request is to fill dinner mains. A lunch dessert claiming a dinner-main constraint also passes the final checker with zero unmet requirements because claimed rows are not checked against that constraint's meal/course. Earlier payload validation catches some such cases, but that does not make the final invariant checker complete. Validate the resolved date/meal/course/count together, and compute gaps after all removals, including duplicate removal. Evidence: [coverage check](../../src/Dishhive.Api/Services/Suggestions/PlanningIntentValidator.cs#L50), [claimed constraint checks](../../src/Dishhive.Api/Services/Suggestions/PlanningIntentValidator.cs#L88); tests `FinalValidation_DessertAloneDoesNotFillRequestedDinnerMain` and `FinalValidation_MustRejectClaimOnWrongMealAndCourse`.

9. **P2 — Browser regression gates accept broken fixture renders (R10/R11).** Adding runtime-error detection to the same fixture tests exposed exceptions on recipes (`map`), recipe detail (`find`), family, statistics, and shopping list (`length`). Statistics and shopping-list baselines visibly contain unfinished pages. The fixture uses a generic `[]` response for unmatched endpoints and an incompatible statistics object; it also does not consistently match the API's enum/DTO shapes. These results establish a defect in the regression evidence, not that the same five pages fail with valid production responses. Supply typed, representative fixtures and reject Angular errors as well as page exceptions before regenerating/approving baselines. Evidence: [fixture defaults](../../src/dishhive-web/e2e/ui-regression.spec.ts#L28), [statistics fixture](../../src/dishhive-web/e2e/ui-regression.spec.ts#L55), [cross-test report](../../artifacts/review-crosscheck/browser-probes.json).

10. **P2 — Scraper update recovery still has failure windows (R14).** A simulated cleanup failure after `_activate` returns HTTP failure but leaves the new version active; the old process is not restarted, so disk state and loaded modules may disagree. Separately, failure to open the lock file leaves the in-process lock held: every later update reports “already running.” Both were reproduced in Linux using mocked package installation and temporary directories. Include initialization in lock cleanup and make post-activation failures either roll back or complete activation/restart consistently. Evidence: [`update_guard`](../../src/dishhive-scraper/app.py), [activation followed by cleanup/state writing](../../src/dishhive-scraper/app.py); probes in [test_scraper_crosscheck.py](../../artifacts/review-crosscheck/probes/test_scraper_crosscheck.py).

Interpret these failures carefully. Saved-recipe runs retained all three required links; they failed because the corpus rejects every allergy warning, including unknown-facts warnings. Some source failures reflect correct removal of Milk-conflicting candidates, followed by an incomplete plan. These are not evidence that every returned recipe violated an allergy. Conversely, the two complete multi-source freezer fallbacks and three complete contradictory-requirement plans are clear failures to preserve or communicate requirements. Diagnostic intent text was disabled, so the exact model interpretation of the contradictory prompt cannot be reconstructed from persisted telemetry.

**Recommended next implementation order**

First close the confirmation commit race and preserve unresolved intent on exceptions. Then normalize fallback attendance/versions and enforce the reviewed acceptance snapshot. Fix lease recovery, chunk budgeting and freezer retry outcomes alongside their PostgreSQL regressions. Repair the browser fixtures and add the actual acceptance journey before relying on screenshot gates. Finish the remaining R7–R14 contracts and documentation, then rerun the focused regressions and repeated live evaluations. Keep the deferred after-correctness features out of that work.
